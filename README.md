# Task Manager API

A Task Manager backend built with **FastAPI** and **SQLModel** for the Techies Lab Python Backend Track (Week 2 assignment). It has persistent storage, JWT authentication, Argon2 password hashing, and role-based permissions (`user` / `admin`).

Interactive documentation is available at **`/docs`** (Swagger UI), including a working **Authorize** button.

## A note on the database (PostgreSQL instead of SQLite)

The assignment specifies SQLite. This implementation uses **PostgreSQL running in Docker** instead.

- The persistence layer is still **SQLModel**; only the engine behind it changes.
- The database is selected entirely through the `DATABASE_URL` environment variable (`app/config.py` → `app/database.py`), so no application code depends on the database engine.
- Every `id` is generated by the database (a PostgreSQL identity/sequence) and is never accepted from a client. Sequences never hand out a deleted row's id again, which satisfies the "ids are never reused" requirement.
- Data is stored in a named Docker volume (`postgres_data`), so it survives container restarts and rebuilds.

## Setup and run

### Prerequisites

- [Docker Desktop](https://www.docker.com/products/docker-desktop/) (includes Docker Compose)
- Git
- (Only for running the API outside Docker) Python 3.12+

### 1. Clone the repository

```bash
git clone <your-repo-url>
cd task-manager
```

### 2. Create the `.env` file

The `.env` file is intentionally **not** committed to Git. Create it in the project root (same folder as `main.py`):

```env
APP_NAME=Task Manager API
DATABASE_URL=postgresql+psycopg://postgres:postgres@db:5432/task_manager
SECRET_KEY=replace-me-with-a-long-random-string
ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=60
```

#### Setting the secret key

`SECRET_KEY` signs your JWTs. Generate a strong random one with:

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

Paste the output as the value of `SECRET_KEY`. Never commit it, and never reuse the placeholder value.

#### Pointing `.env` at the database

`DATABASE_URL` follows this format:

```
postgresql+psycopg://<user>:<password>@<host>:<port>/<database>
```

The correct **host** depends on where the API runs:

| API runs... | Host to use | Example |
|---|---|---|
| Inside Docker (default, via `docker compose`) | `db` (the Compose service name) | `postgresql+psycopg://postgres:postgres@db:5432/task_manager` |
| Directly on your machine (venv / IDE) | `localhost` | `postgresql+psycopg://postgres:postgres@localhost:5432/task_manager` |

The username, password and database name must match the `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB` values in `docker-compose.yml` (`postgres` / `postgres` / `task_manager` by default).

### 3. Start everything with Docker

```bash
docker compose up --build
```

This starts two containers:

- `task_manager_db` — PostgreSQL 16 (with a healthcheck)
- `task_manager_api` — the FastAPI app on port 8000 (waits until the database is healthy, creates the tables on startup)

When you see `Uvicorn running on http://0.0.0.0:8000`, open:

- Swagger UI: **http://localhost:8000/docs**
- Health check: http://localhost:8000/

### Optional: run the API outside Docker

Keep only the database in Docker and run the API on your machine:

```bash
docker compose up -d db
python -m venv venv
# Windows PowerShell:  .\venv\Scripts\Activate.ps1
# macOS / Linux:       source venv/bin/activate
pip install -r requirements.txt
# make sure DATABASE_URL in .env uses "localhost" as the host
uvicorn main:app --reload
```

## Creating the first admin

There is **no API endpoint** that can create an admin, and `POST /auth/register` always assigns the role `user`. The first admin is created from the command line.

With the containers running, in a second terminal:

```bash
docker compose exec api python create_admin.py --username admin --email admin@example.com --password Admin12345
```

Expected output:

```
Admin created successfully.
```

If you are running the API outside Docker, use:

```bash
python create_admin.py --username admin --email admin@example.com --password Admin12345
```

Notes:

- The script refuses to run if the username or email already exists, or if an admin already exists. Further admins are created by promoting users through the admin endpoints (see [Bonus features](#bonus-features-and-how-to-test-them)).
- Change the example password for anything other than local testing.

## Using Swagger (`/docs`)

1. Open http://localhost:8000/docs.
2. Register a user with `POST /auth/register`, or use the admin you created above.
3. Click the **Authorize** button (top right).
4. Enter the `username` and `password` (leave `client_id` and `client_secret` empty) and click **Authorize**.
5. Every protected route is now called with your JWT automatically. Try `GET /auth/me` to confirm who you are logged in as.

Routes are grouped by tag: **Authentication**, **Tasks**, **Administration**, **Health**.

> `POST /auth/login` takes **form data** (OAuth2 password flow), not JSON. The Authorize dialog handles this for you.

## Endpoints

### Authentication

| Method | Path | Description | Access |
|---|---|---|---|
| POST | `/auth/register` | Create a user (role is always `user`; a `role` in the body is ignored) | Public |
| POST | `/auth/login` | Log in with form data, returns a JWT | Public |
| GET | `/auth/me` | Current user, resolved from the token | Logged in |

### Tasks

| Method | Path | Description | Access |
|---|---|---|---|
| POST | `/tasks` | Create a task (`201`, status starts as `todo`) | Logged in |
| GET | `/tasks` | List tasks with filters, search, sorting, pagination | Logged in |
| GET | `/tasks/stats` | Task counts per status (bonus) | Logged in |
| GET | `/tasks/{task_id}` | Get one task (`404` if missing or not yours) | Logged in |
| PATCH | `/tasks/{task_id}` | Partial update (only sent fields change) | Logged in |
| PATCH | `/tasks/{task_id}/complete` | Set status to `done` (`400` if already done) | Logged in |
| DELETE | `/tasks/{task_id}` | Delete (`204`, or `404` if missing or not yours) | Logged in |

Query parameters for `GET /tasks`:

| Parameter | Type | Description |
|---|---|---|
| `status` | `todo` / `in_progress` / `done` | Filter by status |
| `priority` | `low` / `medium` / `high` | Filter by priority |
| `search` | string | Case-insensitive keyword search in the title (bonus) |
| `sort_by` | `due_date` / `priority` | Sort results (bonus) |
| `skip` | int, default `0` | Pagination offset |
| `limit` | int, default `20`, max `100` | Page size |

### Administration (bonus, admin only)

| Method | Path | Description |
|---|---|---|
| GET | `/admin/users` | List all users |
| PATCH | `/admin/users/{user_id}/role?role=admin\|user` | Promote or demote a user |
| PATCH | `/admin/users/{user_id}/disable` | Disable an account |
| PATCH | `/admin/users/{user_id}/enable` | Re-enable an account |

## Permission rules

| Situation | Response |
|---|---|
| No token / invalid or expired token | `401 Unauthorized` |
| Logged in but role not allowed (e.g. a `user` calling `/admin/...`) | `403 Forbidden` |
| A regular user requests a task that belongs to someone else | `404 Not Found` (same response as a task that doesn't exist, so its existence isn't revealed) |
| Admin requests any task | Allowed |

Additional guarantees:

- A regular user can only see, create, edit and delete **their own** tasks. An admin can manage everyone's.
- `user_id` is always taken from the token on creation, never from the request body.
- `get_current_user` reads the user id from the token and then **looks the user up in the database on every request**. If an admin disables an account or changes a role, it takes effect immediately, even if the user still holds an unexpired token.
- `require_roles([...])` is a reusable dependency for restricting a route to specific roles.

## Implementation notes

- **Server-controlled fields:** request DTOs never include `id`, `status`, `role`, `user_id` or `FDATE`. Unknown fields sent by a client (such as `role`) are ignored.
- **`FDATE`:** every task has an `FDATE` field containing a **random 4-digit number (1000–9999)**, generated by the server when the task is created (`app/models.py`). It is not accepted from the client and is returned in every `TaskResponse`.
- **Validation:**
  - `UserCreateRequest`: username 3–50 characters and non-blank, valid email, password of at least 8 characters and non-blank.
  - `TaskCreateRequest` / `TaskUpdateRequest`: a blank or whitespace-only title is rejected with the validation message `TITLE_VALIDATION_17` (returned inside the `422` response; Pydantic prefixes it with `Value error, `). A `due_date` in the past is rejected.
- **Partial updates:** `PATCH /tasks/{task_id}` uses `model_dump(exclude_unset=True)`, so only fields that were actually sent are overwritten.
- **Shared 404 helper:** `get_task_or_404` in `app/routers/tasks.py` is used by every single-task route so all "not found" responses have the same shape: `{"detail": "Task not found"}`.
- **Route order:** `GET /tasks/stats` is declared **before** `GET /tasks/{task_id}` so `stats` isn't parsed as a task id.
- **Responses:** all routes use `response_model`. The password hash is never included in any response.

## Bonus features and how to test them

All of these can be tested directly from `/docs`. Click **Authorize** first.

### 1. Keyword search

Search task titles (case-insensitive, partial match).

- `GET /tasks` → set `search` to `inventory`
- Returns only tasks whose title contains "inventory".

### 2. Sorting

- `GET /tasks` → set `sort_by` to `due_date` or `priority`.
- Can be combined with `status`, `priority`, `search`, `skip` and `limit`.

### 3. Tags

Tasks can carry a `tags: list[str]` field (stored as JSON in PostgreSQL).

- `POST /tasks` with:

  ```json
  {
    "title": "Order shampoo",
    "description": "Wholesale order",
    "priority": "medium",
    "due_date": "2026-12-31",
    "tags": ["shampoo", "wholesale", "supplier"]
  }
  ```

- The response contains the `tags` array. Tags can also be changed with `PATCH /tasks/{task_id}`.
- Filtering by tag is not implemented; tags are stored, returned and editable.

### 4. Task statistics

- `GET /tasks/stats`

  ```json
  { "todo": 4, "in_progress": 3, "done": 7, "total": 14 }
  ```

- A regular user gets counts for their own tasks; an admin gets counts across all tasks.

### 5. Admin user management

Log in as the admin (see [Creating the first admin](#creating-the-first-admin)), then:

| Action | Route | Try it |
|---|---|---|
| List users | `GET /admin/users` | Shows every user (no password hashes) |
| Promote | `PATCH /admin/users/{user_id}/role` | Set `role` to `admin` |
| Demote | `PATCH /admin/users/{user_id}/role` | Set `role` to `user` |
| Disable | `PATCH /admin/users/{user_id}/disable` | User can no longer log in or use an existing token |
| Enable | `PATCH /admin/users/{user_id}/enable` | Restores access |

Safety rules:

- The last remaining admin cannot be demoted.
- An admin cannot disable their own account.
- A regular user calling any `/admin/...` route gets `403`.

## Suggested end-to-end test in `/docs`

1. Create the first admin (command above).
2. `POST /auth/login` via **Authorize** as the admin, then `GET /auth/me` → role is `admin`.
3. Register a normal user with `POST /auth/register` (try adding `"role": "admin"` to the body; the result still has role `user`).
4. Log out and authorize as the normal user. Create a few tasks with `POST /tasks`.
5. Test `GET /tasks` with `status`, `priority`, `search`, `sort_by`, `skip` and `limit`.
6. `PATCH /tasks/{id}/complete` → status becomes `done`; calling it again returns `400`.
7. Create a task as the admin, then as the normal user request it with `GET /tasks/{id}` → `404`.
8. As the admin, `GET /tasks` → sees everyone's tasks; `GET /tasks/stats` → global counts.
9. As the admin, `PATCH /admin/users/{user_id}/disable` for the normal user, then call any route with that user's old token → `401`.
10. Send a task with a blank title (`"   "`) → `422` containing `TITLE_VALIDATION_17`.

## Inspecting the database

```bash
docker compose exec db psql -U postgres -d task_manager
```

Inside `psql`:

```sql
\dt
SELECT id, username, email, role, is_active FROM "user";
SELECT id, title, status, "FDATE", user_id FROM task;
\q
```

To verify persistence: run `docker compose down`, then `docker compose up`. Your users and tasks are still there.

## Troubleshooting

| Problem | Likely cause / fix |
|---|---|
| `Attribute "app" not found in module "main"` | `main.py` must define `app = FastAPI(...)` in the project root |
| `ModuleNotFoundError: No module named 'app.routers'` | `dtos/` and `routers/` must be **inside** `app/`, each with an `__init__.py` |
| `could not translate host name "db"` when running outside Docker | Use `localhost` instead of `db` in `DATABASE_URL` |
| `connection refused` on `localhost:5432` | The database container isn't running: `docker compose up -d db` |
| Swagger login fails with `422` | `python-multipart` is missing from `requirements.txt` |
| `/tasks/stats` returns a validation error about `task_id` | `/stats` must be declared before `/{task_id}` in `tasks.py` |
| Changes to `.env` have no effect | Restart the containers: `docker compose down && docker compose up` |
